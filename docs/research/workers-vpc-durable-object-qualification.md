# Workers VPC + Durable Object qualification research

**Research status: 2026-09-14.** Question: can a Cloudflare Worker with one
Durable Object per sandbox route reach the microvm daemon reliably through a
fixed VPC Service over Cloudflare Tunnel, with `verify_full` origin TLS, and
what remains unproven? Everything below is labeled: **[CF]** = fact from
official Cloudflare documentation (URL + section), **[REPO]** = fact from this
repository or its installed dependencies, **[INF]** = inference (clearly
marked; not documented). Companion decision: [ADR 0001](../adr/0001-in-memory-daemon-and-cloudflare-cutover.md);
operational use: [the Free Vibecode handoff](../handoff/free-vibecode-cloudflare-cutover.md).

## 1. Workers VPC is in open beta [CF]

- https://developers.cloudflare.com/workers-vpc/ — Workers VPC "allows you to
  connect your Workers to your private APIs, services, and databases in
  external clouds … not accessible from the public Internet"; "currently in
  beta. Features and APIs may change before general availability. While in
  beta, Workers VPC is available for free to all Workers plans."
- Open-beta announcement: https://blog.cloudflare.com/workers-vpc-open-beta/
  (VPC Services called the "first milestone"; a unique autogenerated hostname
  per VPC Service listed as *future*).
- Two binding scopes: `vpc_services` (pre-registered specific host/port,
  `binding`, `service_id`, optional `remote: true`) and `vpc_networks`
  (`binding` + `tunnel_id` or `network_id: "cf1:network"`; adds raw TCP
  `connect()`, plaintext-only today).
  https://developers.cloudflare.com/workers-vpc/configuration/vpc-services/
  ("Workers binding configuration"),
  https://developers.cloudflare.com/workers-vpc/configuration/vpc-networks/.
- Service limits: 1,000 VPC Services per account; "Standard Workers limits
  apply for request size, timeout, and subrequests."
  https://developers.cloudflare.com/workers-vpc/reference/limits/.
- Upgrade failures are an anticipated error class:
  https://developers.cloudflare.com/workers-vpc/reference/troubleshooting/
  documents `http_upgrade_failed` — "An HTTP upgrade (for example, WebSocket)
  failed". **[INF]** An error code for failed upgrades is not a promise of
  WebSocket support; treat WS support as unproven until spiked (P0-4).

## 2. VPC Service fixed-host behavior [CF]

Source: https://developers.cloudflare.com/workers-vpc/configuration/vpc-services/
(last updated 2026-06-25; verified in full 2026-09-14).

- A VPC Service is "specific resources in your private network that Workers
  can access through Cloudflare Tunnel"; binding `fetch()` is "securely
  routed to the configured service in the private network" — SSRF-safe, and
  it is *not* a public-hostname publication mechanism (published Tunnel
  applications + Access service tokens are a separate architecture:
  https://developers.cloudflare.com/tunnel/concepts/routing/,
  https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/).
- **Fixed target**: the configured "host and port(s) will always be used to
  connect and route requests", "even if a different host or port is present
  in the URL provided to the `fetch()`". The runtime URL host only populates
  `Host` and, for HTTPS, SNI; the port is ignored. This is the documented
  basis for per-node Runtime Locators: the URL selects nothing.
- Scheme: `http` → plaintext tunnel→origin leg; `https` → encrypted
  tunnel→origin leg with SNI taken from the `fetch()` hostname.
- **TLS trust is restricted**: "publicly trusted certificates" and
  **Cloudflare Origin CA** certificates only. "If your origin service
  presents a certificate that is not issued by a publicly trusted CA or by
  Cloudflare Origin CA, the TLS handshake will fail and `fetch()` will throw
  an exception." A privately issued CA chain is therefore **not** accepted
  under default verification — the daemon hosts must present either a
  publicly trusted certificate or a Cloudflare Origin CA certificate for the
  approved private hostnames.
- **TLS certificate verification mode** — `--cert-verification-mode` /
  config key `tls_settings.cert_verification_mode`:
  `verify_full` = "Verify the full certificate chain and hostname (default)",
  `verify_ca` = chain only (skips hostname), `disabled`. **`verify_full` is
  the VPC Service's mode, not a cloudflared setting.**
- Roles: `Connectivity Directory Bind` to bind from Workers; `…Admin` to
  create services. No Access service-token header
  (`CF-Access-Client-Id`/`-Secret`) is involved in the VPC path.
- **Approved posture for this cutover** [REPO, per issue #1]: two fixed VPC
  Service bindings, one per node (`vpc_services`: `binding` + `service_id`);
  VPC Network bindings (`vpc_networks`) are prohibited on the approved path.
  Code selects the named binding whose `nodeId` is pinned in the DO fence;
  the runtime URL host supplies `Host`/SNI only and never changes the fixed
  destination.

## 3. Cloudflared origin TLS (for the tunnel side) [CF]

Source: https://developers.cloudflare.com/tunnel/reference/origin-parameters/
(last updated 2026-09-11; verified in full 2026-09-14).

- `originRequest` TLS keys are camelCase: `originServerName` (expected
  certificate hostname, default ""), `matchSNItoHost` (default `false`),
  `caPool` (local `.pem`/`.crt` bundle "when a private CA signs the
  certificate and the CA is not in the default trust pool"), `noTLSVerify`
  (default `false`; `true` = "allow any certificate").
- Snake-case spellings (`no_tls_verify`, `no_tls_verify_insecure_skip_verify`,
  `ca_pool`) and the names `verify_full`/`verify_origin` as cloudflared
  settings are **not** documented [CF, via
  https://github.com/cloudflare/cloudflared/blob/master/config/configuration.go
  + docs]. For the daemon origin behind a VPC Service, ingress-level TLS
  hardening is configured on the VPC Service (§2); cloudflared ingress
  remains default (`noTLSVerify: false`).

## 4. Redundant tunnel connectors [CF]

- https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/tunnel-availability/
  — one `cloudflared` makes four outbound-only connections across ≥2 data
  centers.
- …`/tunnel-availability/deploy-replicas/` — run multiple replicas against
  one tunnel (up to 25 replicas / 100 connections); all share routes and
  config; "Replicas do not support traffic steering"; requests go to the
  nearest replica and Cloudflare retries another on failure with no
  guarantee which.
- https://developers.cloudflare.com/workers-vpc/configuration/tunnel/ — VPC
  guidance repeats no load balancing and warns that scaling connectors down
  breaks pinned connections; production baseline: two dedicated replica
  hosts per location, ≥4 GB RAM / 4 vCPU each.
  **[INF]** Two connectors per daemon host is the qualifying posture; a
  single connector is a single point of failure by these docs, not a
  verified runtime failure mode.

## 5. Effect RPC HTTP transport has no durable session [REPO]

From the installed `effect@4.0.0-beta.107` source (verified 2026-09-14):

- `node_modules/effect/src/unstable/rpc/RpcClient.ts` — `makeProtocolHttp`
  sends each RPC `"Request"` as one HTTP `POST`; the terminal response must
  arrive inside that same HTTP response (plain text body when the JSON
  serializer does not frame, or the response stream for stream RPCs).
  Missing terminal response ⇒ `RpcClientError` ("HTTP response ended before
  RPC request completed"). `supportsAck: false`,
  `supportsTransferables: false`.
- `node_modules/effect/src/unstable/rpc/RpcServer.ts` (`makeProtocolHttp`,
  `makeProtocolWithHttpEffect`) — the daemon registers one POST route; each
  request gets its own client id and response queue; when the HTTP request
  scope closes, the server writes `Interrupt` for that connection's
  in-flight request ids. **There is no durable session across HTTP
  requests; a disconnect interrupts in-flight work.**
- `node_modules/effect/src/unstable/http/FetchHttpClient.ts` — the
  fetch-based HttpClient for "browsers, edge runtimes" (workerd);
  `RpcClient.layerProtocolHttp` accepts any `HttpClient`, so the same typed
  client runs on the Node transport or `FetchHttpClient` — which is how
  request-scoped clients stay runtime-neutral.
- **[INF]** Because each RPC is one POST and each response must carry its
  terminal message, a Worker→VPC→Tunnel→daemon round trip per RPC is
  sufficient for the whole contract; no WebSocket or persistent connection
  is required for control-plane RPCs. This is the reason the greenfield
  surface fits the request-scoped Worker model (ADR 0001).

## 6. Durable Objects: eviction forces durable storage [CF]

- https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/
  — "Durable Objects may shut down at any time due to deployments,
  inactivity, or runtime decisions"; no shutdown hooks; on hibernation "the
  in-memory state is discarded"; a non-hibernateable idle object is evicted
  after ~70–140 s; the constructor re-runs on the next invocation.
- https://developers.cloudflare.com/durable-objects/best-practices/access-durable-objects-storage/
  — "use Storage API to persist state durably on disk that needs to survive
  eviction or restart"; memory is only a cache.
- Consequence for the cutover **[INF]**: the one versioned Sandbox Session
  record must live in DO storage and every request must be able to
  reconstruct from it alone — exactly the adapter-state design in ADR 0001
  and the handoff (§4 of the handoff).
- Storage backend: SQLite-backed objects (recommended for all new
  namespaces) expose synchronous `ctx.storage.sql.exec` and synchronous
  SQLite-backed `ctx.storage.kv`; legacy KV-backed objects expose only the
  asynchronous API. Storage is "transactional and strongly consistent
  (serializable)" per
  https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/
  and https://developers.cloudflare.com/durable-objects/reference/glossary/.
  Cursor caveat: fully consume a SQL cursor before awaiting.

## 7. Workers `fetch`: per-request, streaming, WS-capable [CF]

Source: https://developers.cloudflare.com/workers/runtime-apis/handlers/fetch/
and https://developers.cloudflare.com/workers/runtime-apis/request/.

- Each request is one `fetch(request, env, ctx)`; `env` is not per-request
  state ("the same object identity may be passed to multiple requests") —
  so any credential-bearing shared client state must live in scoped
  wrappers, never module globals (matches microvm's Scoped Client rule).
- **No connection-reuse guarantee**: no current page promises keep-alive,
  affinity, or lifetime; the Node `https.Agent` compatibility layer "does
  not support connection pooling or keep-alive" and "Workers will manage
  connections automatically"
  (https://developers.cloudflare.com/workers/runtime-apis/nodejs/https/).
  Treat reuse as an opaque optimization, never a session.
- WebSocket **client** connections are supported via
  `fetch(url, { headers: { Upgrade: "websocket" } })` → `response.webSocket`
  → `accept()`
  (https://developers.cloudflare.com/workers/runtime-apis/fetch/,
  https://developers.cloudflare.com/workers/examples/websockets/) — the
  client role differs from an HTTP *upgrade pass-through*, which is why
  P0-4 is a distinct gate. Repo fact: the installed ingress adapter
  (`src/http-ingress.ts`) implements no upgrade path; whether a DO could
  pass an upgrade through the VPC binding at all remains unverified
  (P0-4).
- Streaming: `RequestInit.body` accepts a `ReadableStream`; response bodies
  can stream after headers
  (https://developers.cloudflare.com/workers/runtime-apis/streams/). Plan
  request-body limits 100 MB/200 MB/5 GB (Free/Pro/Business);
  https://developers.cloudflare.com/workers/platform/limits/.
- At most **six** connections per invocation may simultaneously wait for
  initial response headers (outbound WebSockets count); after headers
  arrive, the connection no longer counts.
- Wall time is unlimited while the client remains connected; `waitUntil()`
  adds ≤30 s; runtime updates allow a 30 s grace.

## 8. workerd vs deployed Workers [CF]

- https://github.com/cloudflare/workerd/blob/main/README.md — workerd runs
  "the same code that powers Cloudflare Workers" but standalone workerd "is
  not a hardened sandbox"; the hosted service adds defense-in-depth.
- https://developers.cloudflare.com/workers/local-development/ —
  Wrangler/Miniflare local dev uses workerd, but bindings connect to
  locally simulated resources; a `remote: true` binding links only that
  binding to the deployed resource; `wrangler dev --remote` uploads code to
  a preview environment. DO bindings cannot be direct remote bindings;
  configured limits "are only enforced when deployed to Cloudflare's
  network" (https://developers.cloudflare.com/wrangler-configuration/#limits
  via https://developers.cloudflare.com/workers/wrangler/configuration/).
  **[INF]** P0 gates must run deployed (real network path), not only in
  local Miniflare — local qualification proves code shape, not the
  network path.

## 9. DO identity, alarms, and limits [CF]

- https://developers.cloudflare.com/durable-objects/api/namespace/ —
  `idFromName(name)` maps a name to a unique object id in that namespace;
  re-deriving the same name addresses the same object. First-use of a
  name-derived ID performs a global check "to guarantee that only one
  instance of the Durable Object is created"
  (https://developers.cloudflare.com/durable-objects/api/id/). The random-id
  method is `newUniqueId()` (no `newUniqueKey` exists). Identity is
  namespace-scoped.
- https://developers.cloudflare.com/durable-objects/api/alarms/ — one alarm
  per object, at-least-once, exponential backoff (2 s, ≤6 retries);
  https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/
  — in-memory `setTimeout`/`setInterval` callbacks prevent hibernation and
  are lost on restart; `waitUntil()` ends ≤30 s after the response. Use
  alarms for anything that must outlive a request. Timers exist inside the
  request context but nothing survives eviction
  (https://developers.cloudflare.com/workers/runtime-apis/web-standards/#timers).
- CPU: DO invocations default 30 s active CPU, configurable to 5 min via
  Wrangler `limits.cpu_ms`
  (https://developers.cloudflare.com/durable-objects/platform/limits/);
  an alarm handler has a 15-minute wall-time limit; an outbound TCP/WS
  connection keeps the object alive at most 15 minutes; plain `fetch()`
  never keeps it alive.

## 12. Explicitly not found in official docs (2026-09-14)

- A Workers VPC-specific guarantee for WebSocket support, WebSocket lifetime,
  or streaming behavior (§1, §7) — the `http_upgrade_failed` troubleshooting
  entry is the only upgrade-related statement.
- A documented, currently-shipped autogenerated public hostname per VPC
  Service (the beta blog lists it as future).
- A generic `vpc`/`network` Wrangler binding key or a `vpc_services` section
  in the main Wrangler configuration reference (keys are documented in the
  Workers VPC pages).
- Any claim that Worker `fetch()` reuses outbound connections.
- A named `verify_origin` mode anywhere.
